## Findings

### 1. The GitHub token claim is out of date

- **Severity:** major
- **Confidence:** 100
- **Section:** 3a, GitHub App; 6.1, pull requests opened by code
- **Evidence:** The funnel says pull requests opened with the default Actions token do not trigger checks. GitHub changed this on **2026-06-11**: pull requests created by `github-actions[bot]` now create workflow runs, but those runs wait for approval by a user with write access. GitHub's current `GITHUB_TOKEN` documentation says the same for `opened`, `synchronize`, and `reopened` pull-request events. It recommends an App installation token or personal token when the runs must start without approval. This factory requires unattended operation, so finishing the App remains a sound call, but the reason is no longer “no workflow run.”
- **Recommendation:** Replace the claim with: “The default Actions token creates approval-gated pull-request workflow runs. The trial needs an App token so required checks start automatically, without a governor click.” Cite GitHub's dated 2026-06-11 changelog and add the approval behavior to the trial question.

### 2. The scorecard is ranked below the funnel's own exit test, and cost is missing from the Must record

- **Severity:** major
- **Confidence:** 96
- **Section:** C12; appendix items 80–82; proposed good-enough line
- **Evidence:** The rank test says the new path must run “unattended, measured.” Register item 81 requires one code-computed scorecard at wave, feature, order, and task level, including acceptance by pass, lead time, unattended rate, cost by role, estimate versus actual, and measurement cost. Yet C12 makes the scorecard and drift signal Should. Its Must description records model, role, work item, time, and tokens where reported, but omits **cost**, which items 80 and 82 require for every run. A raw event stream is instrumentation, not the agreed measured view. The proposed line happens to include Should, but ranks must stand on their own and the governor may move that line.
- **Recommendation:** Make the minimum agreed scorecard and drift signal Must, including cost and the four units. Keep only presentation refinements as Should. State how the provider export produces per-run estimated token and cost records when the runtime supplies no direct usage.

### 3. The held-back acceptance set is silently deferred

- **Severity:** major
- **Confidence:** 98
- **Section:** appendix item 41; C3
- **Evidence:** Register item 41 is one agreed change: requirements by example **with a held-back set** that a fresh evaluator runs. The appendix gives the same row “Must / Later,” putting the evaluator half in Later, while C3 includes only visible examples. The register does not authorize that split, and the funnel does not identify it as a proposed cut for the governor.
- **Recommendation:** Either include a small held-back acceptance set in Must or present its removal as an explicit governor choice with the quality trade-off. Do not record the agreed item as both Must and Later.

### 4. The design kit is custom starting material, not a bought capability

- **Severity:** major
- **Confidence:** 94
- **Section:** C9; appendix items 94 and 104
- **Evidence:** “Bought” is defined as a product capability. The design kit is repository source material under `notes/retro/sources/factory-design-kit/`, with an unexecuted workflow and a roughly 200-line custom controller. Its own comments say it has not been validated or executed. It covers spec and plan review only. The agreed target additionally needs cross-family enforcement, test and code review, task and cause fields, two code-review verdicts, lane-specific seats, git-persisted rounds, and decision escalation. Item 104 requires using the kit as the starting point, but does not turn it into an off-the-shelf product.
- **Recommendation:** Bin C9 as existing custom base + Glue (with Spec Kit providing the bought workflow primitives). Keep the kit because item 104 explicitly requires it, but count and describe the adaptation as custom work.

### 5. Four estimates understate integration and proof work

- **Severity:** major
- **Confidence:** 87
- **Section:** C5, C8, C9, C19; trial gate; roll-up
- **Evidence:** C5's 6/14 hours covers durable cross-job state, safe resume, idempotence, deadlines, two restarts, an outside watchdog, and post-step verification. The survey itself identifies this as Spec Kit's weakest area and says more than a few days of reliability glue should reverse the product decision. C8's 5/9 hours includes about six schemas, validators, one-repair behavior, generated briefs, and code-owned record writing. C9's 6/12 hours extends an unexecuted spec/plan prototype into all review stages and lanes. C19's 4/8 hours removes machinery spread through a 9,675-line Python package plus tests and documentation; repository measurements confirm 29 registered checks and 83 Python files. These are not merely file edits: the rank test requires a proved unattended trial and safe changeover.
- **Recommendation:** Re-estimate after separating implementation from proof. Plausible planning ranges are C5 **12/24**, C8 **10/18**, C9 **10/20**, and C19 **8/16** agent-hours. Treat the current 20-hour trial estimate as optimistic and make the stop/re-estimate gate binding before migration.

### 6. Reconciliation is a safety property, not a Should

- **Severity:** major
- **Confidence:** 91
- **Section:** appendix item 16; C5
- **Evidence:** Register item 16 requires each pass to compare wanted and actual git state and take the next safe, repeatable step, so a missed notice is harmless. Item 12 requires no silent stall and safe recovery, and item 20 permits restarts only from a checkpoint. The funnel ranks reconciliation Should even though C5's Must promises resume, restarts, and a watchdog. Without idempotent reconciliation, those mechanisms can repeat pushes, comments, issue transitions, or pull-request creation.
- **Recommendation:** Make the minimal reconciler behavior in C5 Must. Keep richer reconciliation diagnostics as Should if needed.

### 7. Several appendix bins describe ownership incorrectly

- **Severity:** minor
- **Confidence:** 95
- **Section:** appendix items 11, 49, 59, and 60
- **Evidence:** Item 49 (“few standing agents”) is marked Bought because engine steps are short-lived, but it is a working-role rule and therefore a Habit under the funnel's definition; no product supplies the organizational choice. Item 11 calls writing the failure inventory Glue, although it is a document, not code or a workflow file. Items 59 and 60 are marked Retire even though moving private rules into git and fixing stale documents are content-migration habits; the documents are not necessarily retired. These do not change the selected products, but they overstate how much the product buys and blur the amount of authored migration work.
- **Recommendation:** Re-bin item 49 as Habit, item 11 as Habit, and items 59–60 as Habit plus Retire only where a named old source is actually deleted.

### 8. The capability table has malformed rank/estimate cells

- **Severity:** minor
- **Confidence:** 100
- **Section:** C7, C9, C11, and C12 rows
- **Evidence:** These rows put rank and hours in one cell (for example, “Must 2 / 6”) instead of using the separate Rank and Agent-hours columns. This makes the main decision table harder to scan and obscures which optional estimates feed the Should and Could roll-ups.
- **Recommendation:** Give each row six cells and put separate Must, Should, and Could estimates in the Agent-hours cell.

## What I checked and found fine

### Coverage

I counted the appendix mechanically: items 1 through 104 are present once each, with no missing or duplicate item number. Items 71, 72, 74, 75, and 79 are reasonably marked Done because this retro has already produced the funnel, path lock, cross-family survey, commodity framing, and Wave 2 reconsideration. The principles P1–P18 are carried at a higher level; P18 is explicitly tied to C12.

Apart from findings 2, 3, 6, and 7, the capability mappings are recognizable and preserve the register's intent. In particular, items 86–90 correctly retain three lanes, one switched workflow, and cross-family review in every lane.

### Bins

The main buy-versus-build boundary is sound: Spec Kit supplies the workflow engine, GitHub supplies queue and merge controls, Actions supplies hosting, Logfire supplies telemetry storage, and custom code is limited to lab-specific exchange, review, decisions, and reliability integration. I found no other clear case where the funnel proposes substantial Glue for a capability already supplied end to end by one of the named products.

### Ranks

The core path—intake, engine, host, queue, runtime, structured exchange, review, merge guards, decision pause, rulebook change, reliability trials, and removal—is correctly above the line. Optional fallback runtime proof, scoped re-review, richer governor views, and import lint can safely follow the first usable trial. The burn chart can remain Could provided the minimum scorecard and drift signal move to Must.

### Removals

The retire calls substantially match the survey:

- Orders, amendments, claims, handoffs, the board, and most of the command duplicate GitHub or Spec Kit.
- Decisions and simplified verdicts retain lab-specific culture with no equivalent guarantee in the bought stack.
- Keeping only the irreversible-harm editor hook follows item 35.
- Shrinking the checks and dropping checks-of-checks follows items 25–38.
- The GitHub App now has a valid unattended-CI reason once finding 1's wording is corrected.
- The cutover after a trial order and light change satisfies the known-good-factory rule; nothing is assigned to both queues.

I found no removed function that lacks a named successor. The provisional check audit still needs its planned implementation pass; its present keep/demote/retire calls are coherent with the seven-category blocking set.

### Estimates

The small document/configuration estimates (C1–C3, C6–C7, C10, C13–C14, C16, and C18) are plausible. C11, C12, C15, and C17 are optimistic but remain within their pessimistic ranges if their scope stays narrow. Governor time of 3–5 hours is plausible for settings, secrets, rulebook review, and trial decisions, excluding waiting time.

### Architecture points

1. Correct direction, incorrect current behavior; see finding 1.
2. The proposed resolution of items 31 and 33 is sound: schema/structure blocks, wording warns.
3. Time caps are a defensible implementation of item 84 because the estimates are in agent-hours. The funnel appropriately discloses that individual Cursor plans do not expose direct per-run usage. Finding 2 still applies to the required cost record and scorecard.
4. The named cutover is consistent with items 76 and 78 and avoids dual handling.
5. Checking local template overrides during the Spec Kit upgrade is prudent. The installed repository is on Spec Kit 1.0.6 and has local templates and a workflow, so the trial should verify preservation rather than assume it.

### Leftover stances

All three stances are consistent with the agreed register:

- Sending unresolved work to the governor after round three matches items 7 and 94.
- Replacing product/process tags with an immutable reviewer “needs the governor” mark matches item 94's agreed convergence rule and item 92's target format.
- Letting code validate, commit, push, open the pull request, and start review matches items 91 and 98.
